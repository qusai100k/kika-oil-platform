# الهندسة المقترحة

## القرار العام

تطبيق ويب modular monolith هو الأنسب مبدئيًا: يقلل التعقيد التشغيلي مع إبقاء حدود المجالات واضحة وقابلة للفصل لاحقًا. لا حاجة إلى microservices في الإصدار الأول.

## المكدس

- Next.js App Router + React + TypeScript بإصدارات مستقرة ومتوافقة وقت المرحلة 1.
- Tailwind CSS ونظام مكونات محلي قابل للوصول ويدعم RTL/LTR.
- PostgreSQL وPrisma، مع migrations ومراجعة قيود قاعدة البيانات.
- Zod للتحقق عند حدود النظام، وReact Hook Form للنماذج التفاعلية عند الحاجة.
- حل مصادقة ناضج بجلسات آمنة وتحقق خادمي؛ يُختار بعد حسم متطلبات البريد/الهاتف والاستضافة.
- تخزين كائنات للصور، مزود بريد/رسائل، دفع وشحن وAI خلف adapters تُحدد لاحقًا.

## حدود المجالات

```text
Presentation (Arabic RTL, future i18n)
  -> Application services / use cases
     -> Domains: Identity, Catalog, Commerce, Assessment,
        Recommendation, Consultations, Content, Notifications, Analytics
        -> Repository/provider interfaces
           -> PostgreSQL/Prisma and external providers
```

لا تستدعي الواجهة Prisma أو مزودي الطرف الثالث مباشرة. تظل قواعد الصلاحية والتسعير والمخزون والتوصية داخل خدمات المجال، وتتحقق المدخلات والتفويض في الخادم.

## تنظيم مقترح لاحقًا

```text
src/
  app/                 routes, layouts, metadata
  components/          shared accessible UI
  features/            domain-specific UI and actions
  server/
    auth/              authentication and authorization
    db/                Prisma client and transaction helpers
    domains/            application/domain services
    providers/          payment, mail, storage, AI adapters
  lib/                 small cross-cutting utilities
  i18n/                locale configuration and messages
prisma/                 schema, migrations, explicitly demo seed
tests/                  unit, integration, e2e fixtures
docs/                   decisions and operating documentation
```

البنية النهائية تُضبط بحسب إصدار Next.js المختار، ولا تُستخدم Server Actions أو Route Handlers كبديل عن طبقة التفويض والخدمة.

## نموذج البيانات

الكيانات المقترحة في الموجز صالحة كنقطة اكتشاف وليست مخططًا نهائيًا. يلزم قبل التثبيت:

- تحديد نموذج المنتجات الجاهزة مقابل التركيبات المخصصة والدفعات.
- فصل بيانات الحساب عن الملف، والموافقات ذات الإصدارات، وملاحظات المختص المقيدة.
- حفظ snapshot لاسم/سعر/ضريبة عناصر الطلب وقت الشراء.
- إصدار الأسئلة والخيارات والقواعد والنتائج حتى تبقى التوصية قابلة لإعادة التفسير.
- نمذجة انتقالات الحالات والقيود الفريدة والمعاملات للحجز والمخزون والدفع.
- تعريف الحذف المنطقي/إخفاء الهوية والاحتفاظ بدل cascade غير مدروس.

## الأمن والخصوصية

- جلسات cookies آمنة `HttpOnly/Secure/SameSite` وسياسة CSRF مناسبة لأسلوب المصادقة.
- RBAC مبدئيًا مع فحوص ownership وقيود أدق للبيانات الحساسة؛ الواجهة ليست حاجز أمان.
- أسرار على الخادم فقط، تدوير مفاتيح، وتحقق توقيع webhook مع idempotency.
- تشفير النقل والتخزين لدى المزود، تقليل البيانات، redaction للسجلات، وrate limiting.
- سجل تدقيق غير قابل للتعديل المعتاد للأفعال الإدارية الحساسة؛ لا يُخزن نصوص حساسة دون ضرورة.
- رفع صور مباشر مضبوط النوع والحجم والمسار، وفحص عند الحاجة، دون كشف مفاتيح.

## التوصية والذكاء الاصطناعي

محرك القواعد دالة حتمية بإدخال منظم ونسخة قواعد وإخراج منظم يتضمن النتيجة والاستبعادات والأسباب والتحذيرات والإحالة. تُختبر نسخة القواعد بحالات ذهبية قبل نشرها.

المساعد اللاحق لا يتصل بقاعدة المنتجات بحرية ولا يخترع القرار. يستخرج حقولًا، يمررها للتحقق والفرز والمحرك، ثم يصوغ نتيجة معتمدة ضمن schema. عند الغموض أو فشل المزود تكون النتيجة سؤالًا آمنًا أو إحالة، لا تخمينًا.

## التدويل وRTL والوصولية

- locale جزء من routing/المحتوى، ورسائل الواجهة خارج المكونات قدر الإمكان.
- استخدام الخصائص المنطقية CSS واختبار `dir=rtl` و`dir=ltr`.
- خط عربي مرخص وسريع، تنسيق أرقام/تواريخ/عملات بحسب locale والمنطقة الزمنية.
- HTML دلالي، labels، focus مرئي، contrast، reduced motion واختبارات لوحة مفاتيح.

## الاختبار والجودة

- unit لقواعد التسعير والمخزون والتقييم والتوصية والصلاحيات.
- integration لقاعدة البيانات والمعاملات والمزودين عبر عقود.
- e2e للرحلات الحرجة: تسجيل/طلب/إدارة/تقييم/إحالة/حجز.
- اختبارات سلبية للتفويض، webhooks مكررة، تزامن المخزون والحجز، وفشل المزود.
- lint/typecheck/build، فحص تبعيات، وصولية وأداء في CI.

## التشغيل والمراقبة

بيئات منفصلة، migrations كخطوة نشر محكومة، logs منظمة مع correlation IDs، مقاييس وتنبيهات، تتبع أخطاء، نسخ احتياطية واختبار استعادة. تُحدد RPO/RTO وSLO بعد معرفة حجم العمل وتكلفته المقبولة.

## قرارات مؤجلة عمدًا

مزودو الاستضافة والمصادقة والدفع والشحن والبريد والصور والAI، استراتيجية multi-region، ومحرك البحث المتخصص. تُختار بناءً على البلد والحجم والميزانية، لا قبلها.
